The story so far

Seven short chapters. The dated entries are in the log.

1

The harness was in the wrong place

The day before, Eran had shipped a side project: a small pi-style agent living inside a test CLI on a lab VM. It worked. Getting there took a wheel build, a sync, a module load, a credentials wizard and a reverse SSH tunnel, because the lab firewall wouldn't let the VM reach the LLM.

Looking back, the redundancy was obvious. Every developer already has a capable agent on their own machine. Why rebuild one on every VM?

Instead of having the CLI on the local remote machine, developers usually prefer to work with their own setup and dev machine. … The interface is 100% agent to agent, so it needs to work in a good, efficient way.Eran, the first message
2

Five voices, told to argue

Eran asked for the plan to go to sub-agents and for them to fight about it. Four got the same brief with different jobs. A product lead owned the first five minutes. A security skeptic owned the threat model. A protocol architect owned every token. A contrarian argued, in the spirit of pi, that none of this needed MCP at all. A fifth agent went off to survey open source.

Product"The first five minutes are the product." Under three minutes from install to the first remote command.
Security"The server is the wall." Prompt injection from remote output, and the agent already has bash as you.
Protocol"Four tools, not fourteen." Exit code first, head and tail, a handle for the rest.
Contrarian"You don't need MCP; ssh exists." ssh config, ControlMaster, 1Password's ssh agent.
3

Everyone gave something up

Round two was rebuttals, and it was where the design was decided. Each voice read the other three and changed its mind in public. Security dropped its encrypted vault file after the contrarian argued that a homemade vault is how projects end up with CVEs. The contrarian dropped "MCP later" once product pointed out that approvals and long jobs need a long-lived process anyway. Product gave up its fifth tool and its favourite word, "rig". Protocol dropped server-side shell sessions as hidden state.

What was left is small: a CLI and an MCP server on one core, four agent tools, secrets as references, and OpenSSH under a config Conning generates itself.

4

Learning from open source

Open source got us here, and the best ideas in Conning come from people who solved these problems first. We still want to build our own, because Conning should be one small, lightweight MCP server we can read end to end. That means few dependencies, nothing hidden, and easy to trust with your keys.Eran

The survey found nothing that combines a vault that keeps secrets out of the model, a token-lean exec API, and Windows plus Linux targets. It did find good parts. From 1Password and HashiCorp Boundary we took "access without exposure", from Teleport deny-first policy, from OpenHands the timeout that hands control back instead of killing, and from Desktop Commander and E2B job handles with tail reads. One SSH MCP server measured its own 37 tools at about 43.5k tokens, which became our warning.

5

Locking it in, one question at a time

Eran asked for a walkthrough instead of a document: a summary of each section, then the questions that close it. The first answers pulled the scope in. Conning is a tool for one developer on their own machine, so the team-shareable target file went away. Agents with only bash get the CLI as well as MCP. And the agent should know its own helpers well enough to enrol a new target.

That last answer pushed on a rule all four voices had agreed on: the agent can never add a target. The compromise is that the agent proposes the target, it waits as pending, and Eran confirms it with one keystroke. Eran also cut a round trip: cache the CLI help in the README, so the agent doesn't have to call --help every session.

The sharpest moment was about approvals. Pressing "always allow" on systemctl status must not also allow systemctl stop. Eran's answer was to remember two words, not one, the same lesson as a read-only mode in that side project, which leaked through the test CLI's subcommands.

Remember 2 commands prefix. You see why?Eran
6

First contact

M1 is where Conning started touching machines. It still shells out to plain OpenSSH, but never through your ~/.ssh/config. Each target gets a generated config: the host key pinned under its own alias, strict checking, every kind of forwarding off, and one reused connection so a burst of commands costs one handshake. A password never appears on a command line. ssh asks a tiny helper for it, and the helper reads it from the ssh process's environment.

The hard part was long jobs. A test run can outlive an SSH connection, so a command doesn't run inside the session. It runs detached on the target, in its own process group, writing to a file under ~/.conning/jobs. The agent's read asks for bytes from an offset, so it only ever sees new lines. A signal reaches the whole process tree. Old images without setsid or timeout still work, with less protection. The first version had a bug: TERM killed the wrapper before it could record the exit code. The fix keeps the wrapper alive and signals only the command's group.

# the agent asks for something outside the allowlist run(target="lab-lin1", argv=["pytest","-x","tests/smoke"], wait=0) status=pending_approval id=a:7c1e (human runs: conn approve a:7c1e) # you, in a terminal $ conn approve a:7c1e a:7c1e on lab-lin1 pytest -x tests/smoke [a]llow once, [e] always allow 'pytest tests/smoke', [d]eny: e # the agent polls, and only sees new lines read(id="a:7c1e", wait=20) approved a:7c1e: started lab-lin1=j:3fa9 status=running job=j:3fa9 dur=20.0s +41 lines read(id="j:3fa9", wait=60) exit=0 dur=71.4s out=o:3fa9

Eran's rule for this milestone was blunt: mock as much as possible and keep coverage above 95%. The trick that made it honest is a fake transport that runs Conning's real remote scripts with the local sh against a throwaway home directory. The job logic gets tested for real without a server. Getting to 100% found four bugs a happy-path demo would have missed. A failed fan-out start was listed as a job handle. An agent could save a password target with no secret, which then broke the whole target file. Typing "e" on a command that has no rule to remember approved it anyway. A single giant line of output, such as minified JSON, crashed the output cap.

7

What's next

M2 brings the approval to where you already are: a prompt in the agent client, a live conn watch view, and a desktop notification. It also adds the audit log, conn doctor, conn mcp install with rules that stop the agent going around Conning with raw ssh, and detached jobs on Windows. The goal hasn't moved: your own agent, on your own machine, working on a lab VM as easily as on localhost, without ever holding its keys.

The shape, today

Conning runs next to your agent. Everything the agent does goes through four tools. Nothing outside those four tools can reach a target, and the policy behind them lives in code, not in the prompt.

ToolSignatureBehavior
targetstargets(filter?, check?)One line per target: name, OS, shell, tags, mode, last seen. Never a host, a user or a secret.
runrun(target, cmd|argv, cwd?, wait=30, timeout=3600, max_bytes=8192, grep?)One target, a list, or tag:x. Exit code first, output capped at 8 KB. Past wait it returns a job handle and the command keeps running.
readread(id, wait?, range?, grep?, signal?)Long-polls a job for new lines (j:), slices saved output (o:), checks an approval (a:), or pages a remote file (target:path).
transfertransfer(source, dest)Copies files between your machine and a target over the open connection and checks the sha256. File contents never enter the model's context.

#11 · In a box: the server as a container 2026-10-15

Eran asked for the Docker image next, and the image is the easy part. What took thinking is that a container has neither of the two things Conning leans on: the OS keychain, and a terminal to approve at. Rather than tunnel both in, we split the product along the line it already had. The container runs the half that runs commands: Python, the OpenSSH client, Conning, and one volume at /conning holding targets, pinned host keys and job output. The human keeps the other half on their own machine: conn approve, add, lease and allow run from the host against the same folder, so nothing inside the container can grant trust to itself, and approving in the agent client works as before. Secrets follow the same rule: a keychain: reference now fails inside a container with a sentence naming what does work there, which is env:, op:// or a forwarded ssh-agent, and conn doctor says the same before anything breaks. Lab networks are the one honest rough edge: on Linux --network host reaches them, and elsewhere the container needs a route of its own (D46). CI now builds the image on every pull request and runs conn doctor inside it; a tag pushes amd64 and arm64 to GHCR.

#10 · Ponytail: a smaller codebase, and opencode and pi 2026-10-15

With M2 working, Eran asked what we had overbuilt, without dropping a feature. We measured first: 2,592 lines of code in src, not counting blank lines, comments, docstrings or tests. The fixes were plain. The conn command line had a two-to-five line wrapper per command; it is now one table of one-line handlers. Long word lists, such as the commands that can run anything and the flags the read-only list accepts, were one word per line and are now one string each. The target file's list of allowed keys now comes from the Target fields, so the two can't drift. Small pieces of copied logic got one home: picking a live target, running a short script on either OS, asking yes or no, turning a command into the words policy checks. Dead code went: a function only tests called, a transport method whose answer was always rc == 255, and two fields nothing read. That left 2,407 lines. Then two clients joined conn mcp install. opencode reads MCP servers and permission rules from one JSON file. pi supports MCP servers now, but it has no permission rules, so installing there adds the server and says the agent can still run ssh itself (D45). The total after both is 2,435. Removing whole features is a separate conversation, and the candidates are listed in the PR.

#9 · M2's last two pieces: Windows jobs and one-line setup 2026-10-15

Windows targets used to run each command while the ssh connection stayed open, because Windows OpenSSH ends every process a session started when that session closes. Now a Windows job starts the way a Linux one does. Its wrapper is created through WMI, which puts it outside the ssh session. The wrapper runs the command with stdout and stderr in one file, kills the whole process tree on a timeout or a --signal, and writes the exit code last, so read polls it by byte offset like any other job (D43). Secrets got a fix on the way. The scripts used to travel inside -EncodedCommand, which is a command line any process listing on the machine can show. Now that flag only carries a tiny loader, and the script, injected values included, arrives over stdin. The job's own copy of those values sits in a file only the user can read, which the wrapper deletes the moment it starts. The tests run the real PowerShell scripts against a local pwsh, and on the Windows CI runner that includes the WMI launch itself. The second piece is conn mcp install. For Claude Code, Codex or Cursor, it adds the server and writes deny rules in that client's own format: no raw ssh, scp or sftp, no conn approve, lease or allow, and no reading Conning's config. It merges with what is already in those files, keeps a backup, and changes nothing on a second run (D44). Those rules match the command the agent types, so /usr/bin/ssh would slip past them. They are a guardrail, and the wall is still Conning's four tools.

#8 · First real run: prompts, users and PATH 2026-10-15

Eran's first command on a real machine after M2 merged was a test CLI's status, which isn't on any list, so Conning answered with status=pending_approval id=a:... and a conn approve line to copy. That answer is right for an agent and wrong for a person sitting at the terminal. Now conn run asks right there when it has a terminal (once, always, deny) and prints the result in the same go, with no desktop pop-up. Agents have no terminal, so they still get the id. He had also typed a second machine name before the command, because the CLI's own error hint used lab-lin1 as its example target. The hint now uses the target you typed. And a target name in the command's spot is an error that shows the comma form, lab,lab-lin1, instead of being sent to the machine as a program (D40). Then two more from the same session. conn targets didn't say which user each machine logs in as. It does now, since the user isn't a secret; the host still never shows. A target stays one login, so working as another user means adding the machine again with conn add lab-tester --like lab --user tester, which copies the host, port, OS and tags and asks for that user's password (D41). And his test tool came back not found as root. A job runs in a non-interactive shell that skips the login profile, so anything the profile adds to PATH, like ~/.local/bin, was missing. Jobs now take the PATH a login shell would have and drop the rest of the profile's output (D42).

#7 · M2: approvals where you already are 2026-10-15

M1 merged, and M2 started the same morning. A command that needs approval can now be answered in three places. The agent client asks you before the command is queued: once, always, or deny. That works on both MCP protocol versions, through the SDK's resolver: newer clients get the question back as an input_required result and retry the call with your answer, older ones get it mid-call. Claude first made it opt-in, since the protocol lets a client answer a prompt by itself. Eran turned it on by default: Conning is a general MCP for every agent, and clients without prompts fall back to the other two places (D38). The second place is conn watch, a terminal that prints every command, decision and job exit as it happens, with new output under it, and prompts for anything waiting (D36). The third is conn approve, as before, now with a desktop notification. All three go through one function, so they remember the same rule and leave the same audit entry. That audit log is hash-chained, and conn doctor says if a line was edited (D34). Eran also said yes to a built-in list of safe read-only commands, so uname, df, ps, ip addr or systemctl status run on a new machine without asking. Each one has its own argument check, because a word prefix isn't enough: hostname prints the name but hostname x sets it, and ip addr add changes the network (D39). conn allow and conn deny manage other rules by hand (D35), and conn doctor checks everything Eran's first test tripped over (D37). There are 280 tests at 100% coverage, and a replay against a real sshd checked each answer on both protocol versions.

#6 · First real machine 2026-10-15

Eran ran the M1 branch on his macOS workstation against a lab VM, and it worked: approve the target, run uname, approve the command, read the output. Getting there found real bugs. On macOS the SSH control socket path was too long, so it now lives in a short private /tmp/conning-<uid> and is skipped if it still won't fit. His local agent then wrote up what got in its way. conn run lab uname -a failed because the parser rejected flags after the target, so conn now hands everything after its own options to the remote command (D29). A bad secret printed a traceback; now every error is one line, in the CLI and in all four tools. Running wrote to the config dir, which a sandbox mounts read-only, so output and approvals moved to a state dir (D28). An empty conn ls now says which file it read, and a pending target says why it is still pending. Approving a command now prints its result, without hiding it from the agent. Eran asked for a clean-clone test guide; docs/manual-test.md walks through every tool, and Claude replayed it end to end against a local sshd. There are now 152 tests at 100% coverage. A default read-only allowlist, conn allow, conn doctor and a Docker image are filed as issues for later milestones.

#5 · M1: commands over SSH 2026-10-14

The four tools now work against real machines. run starts a detached job and returns the exit code first, or a job handle once wait runs out. read streams new lines, sends signals, pages saved output and reads remote files. transfer copies with scp and checks the sha256. On the human side, conn add, approve, import, test, rm and lease work, and host keys are pinned when you approve a target. Secrets are redacted from all output, along with their base64, URL-encoded and hex forms. It was checked end to end against a local sshd (D24 to D27). Eran then asked for unit tests with mocks and 95%+ coverage. There are now 138 tests at 100% coverage, and CI fails below 95%. Writing them found four bugs, all fixed.

#4 · The repo and the M0 scaffold 2026-10-14

The repo landed on GitHub, not GitLab: EranYonai/Conning, Apache-2.0 for its patent grant. The first draft PR scaffolds v0.0.1. It adds the conn CLI, an MCP server with exactly four tools, a fail-closed target file, the output cap, and two-word allowlist rules. Tests keep the README's CLI help in sync with the code, and another caps the size of the tool schemas, about 3 KB today. CI runs on Linux, Windows and macOS, and PyPI releases go through Trusted Publishing. Running commands over SSH is M1.

#1 · Idea, debate, design page 2026-10-14

Eran's idea: a control room MCP that vaults credentials for remote test machines and lets a developer's own agent run commands there. Four sub-agents (product, security, protocol, contrarian) wrote positions and then rebutted each other. A fifth surveyed open source: SSH MCP servers, credential brokers, Ansible and pyinfra, WinRM libraries, and agent sandboxes. By round two the four had converged on the shape in this log. A registry check retired Patchbay and Conning took its place. The first design page was published with mocks of onboarding, the agent's view, the watch view and the target file.
